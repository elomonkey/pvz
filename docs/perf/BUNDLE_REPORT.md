# EXT-02: стартовая загрузка и чанки — issue #43

База: `main c18ab84`, Vite 8.3.6 / Three.js 0.187.0 из lockfile. Исходные игровые файлы, SDK, сцена и ассеты не изменены. Сырые данные: [baseline](bundle/baseline.json), [after](bundle/after.json), [проверка стабильности vendor](bundle/cache.json).

## Методика

```powershell
npm ci
npm run build
node tests/perf/bundle-perf.mjs current
```

Скрипт сам поднимает production preview на **4178** (strictPort) и отдельный Chromium 1400×900 с холодным browser context. Первый checkpoint: `window.game`, видимое стартовое меню, два RAF и 250 мс для завершения/CDP-учёта запросов. Затем настоящая кнопка начала смены, итоги/магазин и вкладка оформления, вход Гали, повторный вход, F2, повторный F2 и reload в том же context. Сценарные переходы к итогам/боссу используют существующую консольную API Game; сборка не содержит новых игровых hooks.

Считаются запросы JS/CSS/WebP из `/assets/`, raw-размеры файлов и `gzipSync` **level 6**, все значения — байты, без округления до KiB. Это единая методика для before/after; цифры gzip в консольном выводе Vite могут немного отличаться. `transferred` — фактический CDP encodedDataLength, включая HTTP-заголовки; preview отдаёт JS/CSS с gzip. HTML, процедурные canvas-текстуры и заголовки документа в таблицу ассетов не входят. Время первого кадра/FPS и физические мобильные GPU здесь не измерялись.

Baseline повторно собран из исходных `ui.ts`, `devConsole.ts`, `vite.config.ts` на c18ab84; после замера текущие файлы и сборка восстановлены. Оба отчёта получены одной версией скрипта.

Стартовый JS gzip уменьшился на **1 822 байта / 0,8%**. Самый большой выигрыш — перенос трёх атласов портретов и CSS диалогов за действие «Начать смену»: передача стартовых ассетов в этом preview уменьшилась примерно на **51,7%**. Эти ресурсы загружаются позже, функциональность и качество ассетов сохранены.

После загрузки всех поздних модулей сумма JS составляет 875 291 raw / 230 270 gzip против исходных 871 157 / 227 071. Небольшой рост общей суммы — цена границ сжатия, экспорта общих зависимостей и загрузчиков. Результат снижает первую загрузку, не общий объём всех функций.

## Что загружается и когда

| Чанк after | Raw | Gzip | Момент |
|---|---:|---:|---|
| `three-vendor-DIPWXlEc.js` | 595 424 | 148 517 | сразу, нужен для сцены |
| `ui-shared-DBu8_U5T.js` | 15 772 | 6 019 | сразу, общие данные/DOM helpers |
| `index-Rc4DkMXF.js` | 247 034 | 70 713 | сразу, приложение |
| `bossView-CD6L938m.js` | 15 688 | 4 441 | прогрев после «Начать смену», либо первый запрос диалога из dev API |
| `devConsole-DrCOhXxA.js` | 1 373 | 580 | первый F2 / Backquote |

`bossView-CGY9OVq7.css` (22 511 raw / 4 572 gzip) приезжает вместе с модулем диалогов; перед выполнением JS Vite ждёт его CSS-зависимости. Атласы Гали/Зины/Валеры прогреваются прежним кодом BossDialogueScene после создания view. Саня и Королева используют отдельные баннеры, их прежние ресурсы остаются в стартовой загрузке.

Магазин сохранён синхронным: его отрисовка связана с показом результатов и одноразовой обучающей карточки. Сцена/Three.js нужны уже в меню. Отложены именно поздние view-модули; стандартный игровой старт начинает прогрев диалогов задолго до встречи с боссом, без ожидания в Game.

UI сохраняет синхронные вызовы после первой загрузки. До неё вызовы диалога применяются по порядку; `hideBoss`/`hideAllModals` очищает отложенные вызовы, поэтому поздний import не открывает закрытый диалог. Последовательность F2 во время загрузки учитывается, обработчики кнопок привязываются один раз. Ошибки загрузки логируются, последующий запрос может повторить загрузку.

## Кэширование и граф зависимостей

- JS-запросы after по фазам: меню **3**, начало смены **+1**, магазин **+0**, босс **+0**, повторный босс **+0**, первая dev-консоль **+1**, повторная **+0**.
- В том же browser context reload делает три условных JS-запроса. CDP ExtraInfo подтверждает **304**; передаётся 537 байт заголовков, JS-тела берутся из кэша. Baseline делает один такой запрос / 179 байт. Preview использует `Cache-Control: no-cache`, это revalidation, а не обещание zero-request reload.
- Тестовая правка только текста console.error в UI и повторная сборка меняет hash app, сохраняя **побайтно тот же vendor**. Тестовая правка удалена, повторная сборка вернула исходные hashes after; детали и SHA-256 в cache.json.
- `ui-shared` отделяет общие данные и helpers от app. Manifest проверен DFS по **static + dynamic imports**: циклов нет, поздние модули не импортируют app обратно.

Использован [актуальный build.rolldownOptions Vite](https://vite.dev/config/build-options#build-rolldownoptions) и [группы codeSplitting Rolldown](https://rolldown.rs/reference/OutputOptions.codeSplitting). При изменении конфигурации важно повторять проверку manifest, а не судить по именам файлов.

## Ограничения и следующий шаг

Three vendor остаётся **595 кБ raw**, поэтому штатное предупреждение Vite **сохранено**; `chunkSizeWarningLimit` не менялся. Разделение обязательного для первого кадра Three на несколько файлов само по себе не уменьшит суммарную загрузку. Следующий отдельный шаг — профиль используемых renderer/material/shader-модулей Three и проверка возможности уменьшения их состава без изменений визуала; сейчас такое вмешательство не выполнялось.

Загрузка с одного JS-запроса стала тремя: на реальной сети дополнительная стоимость зависит от соединения и заголовков хостинга. Измерение не обещает конкретного ускорения в миллисекундах или прироста FPS. Первый F2 может ждать сеть; прямой первый вызов босса через dev API тоже может ждать загрузку модуля. В обычном старте действует предварительный прогрев по кнопке смены.

Для релизов нужно сохранять старые файлы с hash в имени, пока могут жить старые вкладки: [Vite описывает случай preloadError после деплоя](https://vite.dev/guide/build#load-error-handling). Постоянный 404/офлайн первого lazy import не решается одной стратегией чанков; автоматический reload/новый экран ошибки требует отдельного продуктового решения. Здесь не менялись SDK, серверные cache headers или игровой сценарий при сетевых сбоях.
